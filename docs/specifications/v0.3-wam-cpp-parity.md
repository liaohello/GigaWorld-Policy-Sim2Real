# V0.3 — wam.cpp parity for the GWP 0.5 artifact

Status: **PASS (conversion and self-check) / BLOCKED (numeric parity)** —
2026-10-23. Blocked by available GPU memory, not by a defect in the artifact.

## Goal

Convert the GWP 0.5 checkpoint to the wam.cpp GGUF format with the official
toolchain, prove the artifact is structurally valid, and compare C++ and PyTorch
outputs on identical input and seed.

## Acceptance criteria

### Conversion

- [x] The wam.cpp source is pinned to a commit and its license recorded (`docs/experiments/upstream-sources.md`).
- [x] The converter runs unmodified apart from the normalization file it is given.
- [x] The artifact is produced by the official converter, not by hand-assembly (F1).
- [x] `wam-inspect` and `wam-validate` both accept the artifact: `valid: true`,
      architecture `gwp05`, `state_dim 14`, `action_horizon 48` (F2).
- [x] Tensor namespaces are complete: `gwp.` 1664, `t5.` 242, `vae.` 82.

### Numeric parity

- [x] Identical inputs are prepared: same frame, same 14-D state, same fixed text
      embedding (as bf16 bits), same `action_noise`, same seed.
- [x] The PyTorch reference output is retained with its own provenance.
- [ ] The C++ path produces an output on those inputs. **BLOCKED.**
- [ ] Per-dimension absolute error is reported against a stated tolerance. **BLOCKED.**

## Blocking condition

`wam-predict` requests 10 835 MiB for a single T5 shard *after* roughly 21.9 GiB
of weights are already resident. On a 24 091 MiB card shared with other users
(≈ 5.6–6.2 GiB in use) the allocation fails with `cudaMalloc failed`. The
upstream README's own reference platform is an 80 GB A800.

Unblocking requires **≥ 22 GiB of free memory on one device** (an exclusive
4090, an L40, or an A800). The prepared inputs mean the parity run is a single
command once such a device exists:

```bash
bash scripts/infer/wam_compare.sh     # inspect -> validate -> predict -> compare
```

## Attempts already ruled out

Five configurations were tried and are recorded in
`docs/experiments/robotwin-gwp-native-results.md` (defect F-3): bf16 on CUDA
(OOM), bf16 on CPU (rejected: the BF16 latency profile requires CUDA), f32 on
CPU with a bf16 artifact (rejected: f32 execution requires an f32 artifact), f32
on CPU with the f32 artifact (`resource_exhausted` while loading resident
weights), and f32 on automatic device selection (OOM). Host RAM, GGUF tensor
prefixes, and cgroup limits were each checked and excluded as causes.

## Explicit non-goals

- No quantization beyond the official `mot-vae-bf16` and `source-f32` policies.
- No modification of wam.cpp's normalization semantics to make numbers match;
  the normalization reconciliation lives in the PyTorch side and is documented as
  an algebraic identity, not a fudge factor.
