# V0.3 — wam.cpp parity for the GWP 0.5 artifact

Status: **PASS (conversion and self-check) / BLOCKED (numeric parity)** —
2026-10-23. Blocked by available GPU memory, not by a defect in the artifact.

## Goal

Convert the GWP 0.5 checkpoint to the wam.cpp GGUF format with the official
toolchain, prove the artifact is structurally valid, and compare C++ and PyTorch
outputs on identical input and seed.

## Acceptance criteria

### Conversion

- [x] The wam.cpp source is pinned to a commit and its license recorded (`docs/experiments/upstream-sources.md`).
- [x] The converter runs unmodified apart from the normalization file it is given.
- [x] The artifact is produced by the official converter, not by hand-assembly (F1).
- [x] `wam-inspect` and `wam-validate` both accept the artifact: `valid: true`,
      architecture `gwp05`, `state_dim 14`, `action_horizon 48` (F2).
- [x] Tensor namespaces are complete: `gwp.` 1664, `t5.` 242, `vae.` 82.

### Numeric parity

- [x] Identical inputs are prepared: same frame, same 14-D state, same fixed text
      embedding (as bf16 bits), same `action_noise`, same seed.
- [x] The PyTorch reference output is retained with its own provenance.
- [ ] The C++ path produces an output on those inputs. **BLOCKED.**
- [ ] Per-dimension absolute error is reported against a stated tolerance. **BLOCKED** — the
      tooling exists (`scripts/infer/wam_compare.py`), the measurement does not.

## Blocking condition

What was observed, stated as narrowly as the log supports:

- On a 24 091 MiB card with ~5.6–6.2 GiB held by other tenants, `wam-predict`
  aborted with `cudaMalloc failed` while requesting 10 835 MiB for one T5 shard.
- Roughly 21.9 GiB of the artifact had been made resident before that request.
- The upstream README's own reference platform is an 80 GB A800.

What that does **not** establish:

- It does not prove the peak working set of a complete inference. The failing
  allocation happened during load; nothing here measures the transient memory used
  by activations, the VAE decoder pass, or the diffusion steps.
- Therefore **"≥ 22 GiB free" is an estimated attempt condition, not a validated
  requirement**. A run that fails at 22 GiB would not contradict anything recorded
  here, and a run that succeeds at 20 GiB would not either. Only a run settles it.

The honest wording for planning is: *try a device with at least ~22 GiB free, and
expect the first attempt to be informative rather than definitive.*

## Running the parity check when a device exists

Inputs are already prepared (`cpp_input.npz` with `action_noise` and the bf16
text embedding; `torch_action.npy` from the PyTorch reference):

```bash
bash scripts/infer/wam_infer.sh
# inspect -> validate -> predict(cuda) -> predict(cpu) -> wam_compare.py
```

`wam_infer.sh` exits non-zero when no C++ action file is produced (code 3) and
prints the reason; it does not finish quietly. When a C++ output exists it calls
`scripts/infer/wam_compare.py`, which reports per-dimension error and applies a
tolerance only if one is supplied:

```bash
MAX_ABS_TOL=0.02 bash scripts/infer/wam_infer.sh
```

No tolerance is baked into the repository, because nobody has yet measured what
bf16-on-CUDA versus f32-on-CPU costs on identical input. Choosing one now would be
a number without evidence.

## Attempts already ruled out

Five configurations were tried and are recorded in
`docs/experiments/robotwin-gwp-native-results.md` (defect F-3): bf16 on CUDA
(OOM), bf16 on CPU (rejected: the BF16 latency profile requires CUDA), f32 on
CPU with a bf16 artifact (rejected: f32 execution requires an f32 artifact), f32
on CPU with the f32 artifact (`resource_exhausted` while loading resident
weights), and f32 on automatic device selection (OOM). Host RAM, GGUF tensor
prefixes, and cgroup limits were each checked and excluded as causes.

## Explicit non-goals

- No quantization beyond the official `mot-vae-bf16` and `source-f32` policies.
- No modification of wam.cpp's normalization semantics to make numbers match;
  the normalization reconciliation lives in the PyTorch side and is documented as
  an algebraic identity, not a fudge factor.
